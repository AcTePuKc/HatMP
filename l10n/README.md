Language packs are JavaScript files named for their locale, such as `es.js` or `pt-BR.js`. Each file registers a JSON-shaped data object in `window.HatMPLocales`; it should contain data only, with no executable translation logic. Add the locale and its native display name to `languages.js` so it appears in the game's language selectors.

Packs use `.js` so the game can load them as regular scripts when opened directly from disk (`file://`), where browsers restrict fetching separate JSON files. Since a script can execute code, language pack contributions should be reviewed before they are included in a release.

## Pack format

```js
window.HatMPLocales = window.HatMPLocales || {};
window.HatMPLocales.es = {
  "_meta": {
    "locale": "es",
    "nativeName": "Español",
    "direction": "ltr",
    "author": "Translator name",
    "translator": "Translator name",
    "packVersion": "0.1.0",
    "targetGameVersion": "0.28.3",
    "lastTestedGameVersion": "0.28.2",
    "fallbackLocale": "en",
    "completeness": "partial"
  },
  "strings": {
    "ui.language": "Idioma"
  },
  "names": {
    "lola": { "source": "Lola", "display": "Лола" },
    "eva": { "source": "Eva", "display": "Ева" }
  },
  "terms": {
    "landlady": {
      "display": "Casera",
      "lower": "casera"
    },
    "coTenant": {
      "plural": "Compañeras de piso",
      "pluralLower": "compañeras de piso",
      "singular": "Compañera de piso",
      "singularLower": "compañera de piso"
    }
  }
};
```

The game loads the selected pack and uses English for any missing key. A game-version mismatch is reported in the browser console; it does not prevent the pack from loading. Update `packVersion` when publishing a revised pack and `lastTestedGameVersion` after checking it against a game build.

## Character names

Use the `names` section for locale-specific spellings or transliterations of proper names. Each entry needs the game's canonical source spelling and the spelling to show in that locale. The shared `sc.n("lola")` helper applies the selected spelling wherever the game asks it for that character's display name, including name lists. A player-customized name is kept as entered. Names written directly into a sentence as literal text must be moved to a translation key and placeholder before this mapping can affect them. Translate titles or relationship words as part of a character's display label only when that whole label is the character's canonical name; use `terms` for role words that appear in dialogue and need grammatical forms.

Use explicit descriptive `l10nKey` values on translated chat entries and choices, such as `lola.massage.opening` and `lola.massage.begin`. The runtime can derive a room/chat key as a fallback while migrating old content, but new translated lines should have explicit IDs so moving dialogue within a room does not break translations. Put the entire sentence in the translation and use `{placeholder}` tokens for character names or changing values so translators can move them to fit their language.

## Character phone guides

Phone guide strings use stable character and mission IDs rather than array positions. Use `phone.characterGuide.<characterId>.<missionId>.title` and `.description`, with tasks keyed by their task ID as `.task.<taskId>`. Ending mission IDs begin with `ending_` in localization keys (for example, source mission `*wife` uses `ending_wife`). Missing keys fall back to the original English guide text, so packs can translate a few guides at a time. Keep the English source strings in `en.js` alongside each translated batch. Guide source strings and translations can use `{characterId}` placeholders (such as `{lola}` or `{landlord}`); the phone guide renderer supplies the current localized or player-customized character term.

## Player-entered relationship words

Room 2 lets the player choose what to call the landlady and what Lola and Eva are to them. Locale `terms` provide starting suggestions only. The player's edits take precedence and are saved with the game, so a language pack cannot replace a custom choice. The landlady field collects one word or form of address; capitalization can be derived, but grammatical forms cannot. Its optional advanced field lets the player provide a form such as the definite form when a translation needs it. The co-tenant relationship asks for both plural and singular forms. Bulgarian can suggest a few common patterns and exact exceptions, but the player must review them; unknown forms remain editable. Give locale-specific examples so players know to enter the forms they want to use, such as Bulgarian `сънаемателка` / `сънаемателки` or `съквартирантка` / `съквартирантки`—not a whole phrase such as “your co-tenant.” Existing code that calls `sc.n("el")` or `sc.el()` gets the singular form. New translated sentences that refer to both people should request `sc.els()` for the plural form.

Capitalization and lowercasing can be derived with locale-aware text operations. Grammatical forms such as singular, plural, definiteness, possession, or case cannot be guessed reliably. When localizing sentences that use these values, translate the complete sentence and pass the exact needed form as a placeholder. Rephrase around the provided singular or plural when possible (for example, Bulgarian `някоя от своите {els}` uses the saved plural form). Do not append endings in JavaScript or assume a player's custom word can be declined. If a translation truly needs another form, the game must collect or otherwise obtain it rather than guessing.

Exact Bulgarian input suggestions live in `bg.js` under `formSuggestions`: `coTenantSingularFromPlural` maps selected plural labels to singular labels, and `landladyVocative` maps base labels to the address form. These are internal suggestions, not examples shown in the interface. Add an exception there only when its form is certain; manual player edits always win. The conservative general Bulgarian suffix rules remain in the setup and phone code.

### Extra relationship forms and save compatibility

**Known compatibility note — older saves with custom relationship names:** Older saves may contain custom base names without the optional grammatical forms added later. Standard defaults already have localized forms; custom names without them fall back to the base name and can sound ungrammatical in Bulgarian or Spanish. Players who want the additional forms should open Phone → Characters/Relationships → relationship terms, review singular/plural and landlady forms, fill in the appropriate fields and save. Bulgarian suggests supported forms only when the corresponding base field is edited; suggestions require review and never replace manually edited or previously saved forms. Opening an old save alone does not generate forms. Custom names and extra forms are currently stored globally rather than per language, so changing language may require reviewing them again. English has no demonstrated occurrence of these extra-form placeholders in its current catalog, but custom terms and future English uses still need contextual QA. Future languages must be assessed individually; this is not a claim that every language is affected.

The current saved character data uses `display` for the co-tenant plural and `singularDisplay` for the singular. Those fields remain unchanged. Extra forms live in the optional `relationshipForms` object on the `el` and `landlord` characters, are saved only when customized, and are loaded only when present. Old saves need no migration: their existing names and relationship words remain intact, and missing extra forms fall back to the corresponding base form.

Locale `terms.coTenant` and `terms.landlady` can define extra, language-specific forms as additional string properties. The current packs provide `singularDefinite` and `pluralDefinite` for co-tenants and `definite` for the landlady; the optional setup disclosures and Phone → Relationships editor show forms defined by the active language. Add a matching `relationship.form.<formId>` string to localize each field label. A locale that does not define an extra form will not ask players for it.

In translated dialogue, use stable form placeholders directly in the localized sentence, such as `{els:pluralDefinite}` or `{landlady:definite}`. These resolve through `sc.els("pluralDefinite")` and `sc.landlady("definite")`, so a player's saved form is used; if the locale does not provide that form, the resolver falls back to the plural or display base. Singular forms use `{el:<formId>}` and fall back to the singular base. Existing simple placeholders such as `{el}` and `{els}` continue to work unchanged. Keep sentence-level grammar in the translation; do not append endings to player-entered words in JavaScript.

Use `{landlady:definiteLower}` when the definite form needs lowercase, for example in the middle of a Bulgarian sentence. It lowercases the selected definite form, including a custom one; if no custom definite form is supplied, it uses the same fallback as `{landlady:definite}` before changing case. Use `{landlady:definite}` at the start of a sentence when the stored form has the desired capitalization.

For direct Bulgarian address, use `{landlady:vocative}` after a comma and `{landlady:vocativeCapitalized}` at the start of a sentence or choice. The BG relationship editor exposes an optional vocative field with the default example `хазайке`. Some custom names receive a suggestion; a saved custom vocative always wins. English and Spanish can keep the plain `{landlord}` in direct address.

### Agreed implementation plan

- Keep the existing singular and plural fields as the required, player-facing relationship labels. Use locale-specific, non-familial examples, such as `сънаемателка` / `сънаемателки` or `съквартирантка` / `съквартирантки`, rather than complete phrases.
- Audit translated dialogue and UI to identify which additional grammatical forms are actually needed. Prefer rewriting a sentence to use an available form; add a form only when the language requires it.
- Provide any additional forms through one shared resolver and stable placeholder names. Do not add endings to custom words in individual room scripts. Languages that do not need a form should fall back to their existing singular/plural values.
- Let players fill additional forms in an optional advanced section in new-game setup and in the existing Phone → Relationships editor. Localize its labels and examples for each language.
- Keep all new save fields optional. Old saves must retain the player's existing words, load without a migration prompt, and use safe fallbacks when extra forms are absent. If a first-load notice is added, make it dismissible and offer “Edit now” / “Later”; explain where the editor is and that the save is unchanged unless the player edits it.
- Check English, Bulgarian, and Spanish first, then use the same form system for French, Italian, and German.

## Player pronouns and grammatical agreement

Implemented by `scripts/l10n-format.js` and the shared `l10n.t()` resolver. Use this syntax **inside a normal string value**:

```js
// Spanish: one inflected word.
"example.ready": "Estoy [[player:listo|lista]].",

// Bulgarian: multiple words in the same sentence.
"example.arrival": "[[player:Дошъл|Дошла]] си [[player:сам|сама]], {me}.",

// A phrase or complete sentence may have its own word order and markup.
"example.sentence": "[[player:<b>{me}</b> está listo.|Está lista <b>{me}</b>.]]"
```

The order is always **masculine first, feminine second**: `[[player:masculine|feminine]]`. The selector always refers to the player, regardless of who speaks the line. It follows the existing Phone → Settings pronoun choice: `m` uses the first alternative, `f` the second, and `a` calls the game's existing `gender.isGirl()` appearance rule, including its special ambiguous-appearance handling. Selection happens each time the message is translated. No new save fields or migration are needed. If called before gender initializes, the first alternative is used temporarily.

### Player name and feminine name

New-game setup stores the player's current name (`me`) separately from the chosen feminine name (`girlname`). The pronoun preference controls grammatical agreement; it does not rename the player. Use `{me}` for the player's currently active name. The story's name-change event in Room 910 makes `girlname` the active `me` name and swaps the previous name into `girlname`. This is an in-game event, not a language-dependent rule: translators should not switch names based on the pronoun preference or appearance. Use `{girlname}` only when the source specifically refers to the feminine name before that change; after Room 910 it can contain the former name. If a language needs gendered wording, use `[[player:...|...]]` around the word, phrase, or sentence while keeping the correct name placeholder. The player branch always follows the selected pronoun preference, regardless of the current name or whether the Room 910 name-change event has happened. Do not inflect a player-entered name by adding endings; rephrase the sentence or request a separate form if the game later supports one.

Translators control the scope: use one word, a phrase, or the whole sentence. Multiple branches in a line all follow the same player selection. Keep normal placeholders (`{me}`, etc.) and relationship forms (`{el:singularDefinite}`, etc.) inside or outside either alternative. Markup may also occur inside a branch, provided **both complete rendered sentences** have valid markup. Selection happens before placeholder substitution; names and other player-entered values remain escaped and are never interpreted as branches.

Both alternatives must be nonempty. Use complete words rather than an empty suffix branch: `[[player:listo|lista]]`, not `list[[player:o|]]`. Nested branches and other selectors such as `[[speaker:...]]` are not supported. A literal pipe inside an alternative must be `&#124;`; literal double square brackets in rendered prose can use `&#91;&#91;` / `&#93;&#93;`. Single brackets, such as `[Continue]`, are unchanged. Do not put executable JavaScript or masculine/feminine objects in the catalog.

If a selected translation has malformed branch syntax or a non-string value, the runtime logs a warning once and tries the legacy root entry, English catalog, then source fallback. If all available templates are invalid, it shows the translation key rather than broken grammar syntax. Missing translations retain the existing English fallback. This validates branch structure, not the correctness of the wording; run the checker for markup and placeholder errors too.

### Deciding what should vary

Use `player` only for grammatical agreement **about the player**, where the original line leaves that wording open. It works in dialogue, choices, and UI/guide text that goes through `l10n.t()`. It does not automatically rewrite ordinary strings, image text, or every English `gender.pronoun()` call.

- Prefer natural neutral wording when it works. Add alternatives when the target language requires or benefits from agreement.
- Read the English source and speaker/choice context before editing. A key name such as `myDare` does not prove the player is speaking.
- Preserve an NPC's own gender and references to other people. This selector does not mean “current speaker.”
- Preserve intentionally gendered story language, roles, anatomy references, and characterization. Do not make a setting silently rewrite what a character is meant to say.
- Do not add suffixes to player-entered names or relationship labels; use the existing supplied relationship forms.

### Required workflow for every translation or QA session

Treat grammatical agreement as part of the translation process, not as a later optional polish. Every newly translated line must be checked before it is considered done. For existing translations, a room or key is not considered reviewed until its player-related agreement has been checked, including cases intentionally left unchanged.

At the start of a resumed session, read this section and the progress note below. Work in room-sized batches and, for each dialogue line, identify who the wording describes before choosing a form: the player, an NPC, or another person. Use `[[player:...|...]]` only when the wording refers to the player and the target language needs different forms. The alternatives may be a word, phrase, or complete sentence. Keep NPC and third-person agreement tied to the person in the story. Use supplied relationship forms for player-entered labels rather than trying to infer their endings.

Before closing a batch, run the localization checker and inspect both player variants for the changed lines. Record the locale, room/key range reviewed, any intentionally unchanged candidates that could be mistaken for player agreement, and the next exact room/key to process. Update the progress note in the same change as the translation. Never mark an entire room reviewed based only on a search for obvious adjective endings; read the surrounding scene and choices. Older translations remain **unreviewed** until recorded here, even if they already read naturally.

## Role-play honorifics and family references

Distinguish an actual family relationship from an explicitly fictional role-play title. In sissy-training and BDSM role-play scenes, keep terms such as “Mommy,” “Daddy,” and their locale equivalents when characters use them as consensual role-play titles; do not sanitize them solely because the words can also describe relatives. For example, Room 213 chat 23 uses “mommy dommy” and “daddy dommy” as dom role-play, not as family relationships. Preserve literal family relationships and the established relationships between NPCs; do not replace them with generic terms merely to make the dialogue more neutral. Adjust a relationship reference when it would assign an unsupported family role to the player, since that can impose a story choice the player did not make. Avoid introducing family relationships that the source does not establish.

## Other character term forms

Use `strings` for complete sentences and `terms` for recurring character labels or role words that need different forms in a sentence. Form names are chosen by the language pack; common examples include `display`, `lower`, `plural`, `pluralLower`, or a language-specific form such as `possessive`. Do not build translated sentences by adding suffixes to a term in JavaScript. Player-entered co-tenant singular and plural forms may be typed in ordinary lowercase; use `sc.el("capitalize")` or `sc.els("capitalize")` at sentence starts and `sc.el("lower")` or `sc.els("lower")` where lowercase is required. The default calls preserve the player's entered casing.

When a translated line needs a particular form for a code-defined term, request that form in the game code and pass the returned text as a normal placeholder:

```js
var jobTitle = l10n.characterTerm("jobTitle", "lower", currentTitle, "Foreman");
l10n.t("dialogue.job.intro", "She works as a {title}.", { title: jobTitle });
```

`characterTerm` uses the selected pack's form, then English, then the source value. It compares the current value with the source default so a player's custom label is preserved. A custom label can be lowercased on request; other inflected forms cannot be inferred reliably, so use it as entered unless the player provides those forms separately. Keep proper names as ordinary placeholders; use term forms for role words such as `Landlady` or `Co-Tenant`.

The introductory screen is a good reference for long translated text. Chat bubbles wrap naturally and the dialogue panel can scroll when the translated text is taller. Keep intentional paragraph breaks; do not copy English line breaks into a translation when the language needs different wrapping.

## Carnal Union / C.U.M.

The antagonistic group is formally the **Carnal Union of Mortals**, abbreviated **C.U.M.** The acronym is also the English slang word “cum,” so keep `C.U.M.` in Latin letters in Bulgarian and Spanish rather than inventing a forced local acronym. At the first full-name mention, use **„Съюз на плътските смъртни, известен още като C.U.M.“** in Bulgarian and **«Unión Carnal de Mortales, también conocida como C.U.M.»** in Spanish. Later references can use forms such as **култът C.U.M.**, **комплексът C.U.M.**, **el culto C.U.M.**, or **el complejo C.U.M.** Translate ordinary uses of “cum” according to meaning (for example, „сперма“); do not treat those as references to the organization. Keep this naming consistent in dialogue, inventory text, phone text, and character guides.

The **Church of the Unification of Men** is a church name that also forms the initials **C.U.M.** Keep that acronym in Latin letters in Bulgarian and Spanish too (for example, **Църквата на обединението на мъжете (C.U.M.)** / **Iglesia de la Unificación de los Hombres (C.U.M.)**). The story later links the church to the C.U.M. cult, so preserve the shared acronym without replacing the church's name with the cult's full name.

For occasional contextual hover help in dialogue, wrap the term in `<abbr class='l10n-term' tabindex='0' data-glossary-id='...'>...</abbr>`. The glossary entry supplies the displayed term and tooltip text, so do not copy its definition into each dialogue. Native browser tooltips need no save data; keep them sparse and concise. Keyboard users can focus the abbreviation, and the dotted underline signals that it has extra information.

### Add a glossary entry

1. Choose a short, stable ID in `scripts/localization.js` and register it in `glossaryDefinitions`, pointing to `glossary.<id>.term` and `glossary.<id>.description`.
2. Add both keys to every locale catalog (`l10n/en.js`, `l10n/bg.js`, `l10n/es.js`, and any other maintained locales). Translate the term and write a brief explanation without unnecessary spoilers. The Help → Glossary page reads these entries from the same registry.
3. At a useful first mention in dialogue, add `data-glossary-id="<id>"` to an `<abbr>` around the term. For example:

   ```html
   <abbr class='l10n-term' tabindex='0' data-glossary-id='purityApp'>Purity App</abbr>
   ```

   The markup connects the dialogue to the localized glossary entry; do not add the explanation to the dialogue itself. Add annotations only where a reader may need context, rather than marking every later mention.
4. Add the annotated dialogue location to the review list below. Check the tooltip and the glossary page in the game for each maintained language.

If an ID is misspelled or not registered, the dialogue keeps its original term and remains readable, but no tooltip is added. The game logs a warning once for that ID. If both the selected locale and English are missing a term or description key, the glossary logs a warning and uses the ID or a blank description instead of showing a raw localization key.

## Map labels

Map destination labels have room for one line only. Keep them short and prefer a familiar place name over a full descriptive phrase. As a working limit at the current map size, aim for **up to 15 Latin characters** or **up to 14 Cyrillic characters**, including spaces. These are approximate character budgets, not strict width guarantees: Cyrillic letters, accents, capitalization, and other scripts can take more horizontal space. For reference, Spanish `Entrada de PI` (13 characters) fits with a little room left, while Bulgarian `Входът на Миси` (14 characters) is close to the available width. If a language uses wider glyphs, use a shorter label. Check labels in the running game and shorten any that look cramped or trigger smaller text.
